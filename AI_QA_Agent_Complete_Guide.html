0. How to Use This Guide

This guide is written for two lanes of readers:

  • 🟦 Manual testers: plain English only. Every step says exactly what to click/type; jargon is explained in the Glossary (Appendix B).
  • 🟩 Automation testers / SDETs: you additionally receive runnable Playwright/Cypress/k6 artifacts, a custom Langflow tool component, and CI‑friendly file outputs.

Conventions: 💡 tip ⚠️ critical rule 🔒 security. Follow the steps in order — each one builds directly on the previous.

Also required: 10 GB+ high‑speed SSD (model weights + vector indices); multi‑core CPU with AVX2 (modern Intel/AMD) or Apple Silicon, or an NVIDIA GPU for faster inference; Python 3.10 / 3.11 / 3.12 only — this is the supported range for the orchestration stack.

💡 Quantization explained: "Q4" means 4‑bit compressed weights — about 4.7 GB instead of ~14 GB for a 7B model, with only minor quality loss. This is why serious LLMs fit on consumer hardware.
💡 Model sizing guidance: 8 GB RAM → qwen2.5:3b; 16 GB → qwen2.5:7b (default); 32 GB+/GPU → qwen2.5:14b; script‑heavy work → add qwen2.5-coder as a second model used only for automation tasks.

4. Step 2 — Install the Ollama Engine & Models

  1. Download and install the runtime from ollama.com.
  2. Pull the three models the workstation needs: 
    ollama pull qwen2.5:latest        # core reasoning brain
ollama pull qwen2.5-coder:14b     # high-fidelity scripting brain (Playwright/Cypress)
ollama pull nomic-embed-text      # dedicated RAG embedding model (vectors only)
  3. Verify: open http://localhost:11434 → you must see "Ollama is running".
  4. Network check: confirm the service is not reachable from another machine on your network.
🔒 The Loopback Mandate: Ollama (11434) and Langflow (7860) must stay bound to 127.0.0.1 ("this machine only"). Binding to 0.0.0.0 ("anyone on the network") would expose proprietary requirements and test strategy. If you ever must expose a port, firewall + authentication are mandatory.

5. Step 3 — Install & Launch Langflow

pip install langflow -U        # install the orchestration framework FIRST
python -m langflow run         # then start the workbench
  1. Open http://127.0.0.1:7860.
  2. Click New Flow → Blank Flow and name it QA‑Agent.
💡 Use a virtual environment (python -m venv qaenv, then activate) to keep dependencies isolated. Port busy? lsof -i :7860 → kill the PID, or run python -m langflow run --port 7861.

6. Step 4 — Build the Memory: RAG Ingestion

Why RAG? Chat boxes have small context windows and no long‑term memory. RAG (Retrieval‑Augmented Generation) converts your spec documents into searchable vectors so the agent can look up evidence for every answer — don't paste docs into chat; let the agent read the source.

Wire these components in this exact order:

  1. File/URL Loader → local PDF / Markdown / JSON requirements.
  2. Recursive Character Text Splitter → Chunk Size: 1000, Overlap: 200.
  3. Ollama Embeddings → select nomic-embed-text.
  4. Vector Store (Chroma) → receives splitter + embeddings; set collection name e.g. qa_specs.
💡 Why 1000/200? ~1000‑character chunks are small enough for precise similarity search, while a 200‑character overlap prevents an acceptance criterion from being cut in half between chunks.
⚠️ Critical rule: the Collection Name and Search URL must match exactly between Ingestion and Retrieval flows, and nomic‑embed‑text must be selected on both sides. Vectors made by one model/collection cannot be searched by another — mismatches fail silently as "no context found".

Retrieval wiring: add a Chroma Retriever (same collection) in the operations flow and connect it to the Agent's Tools port, so the agent decides when to consult your documentation.

7. Step 5 — Build the Agent Brain & Tools

Core wiring: Chat Input → Agent → Chat Output. Connect the Ollama component (qwen2.5:latest, or 14b for complex tasks) to the Agent's Model input. Set Tool Mode Enabled → ON.

Tool 1 — Write‑to‑File (paste into a Langflow Custom Component):

import os
from langflow.custom import CustomComponent

class WriteToFile(CustomComponent):
    display_name = "Write to File Tool"
    description = "Allows the agent to write scripts (.spec.ts, .js) or reports (.md) to the local disk."

    def build_config(self):
        return {
            "file_path": {"display_name": "File Path",
                          "info": "Full local path including filename (e.g., ./output/test.spec.ts)"},
            "content": {"display_name": "Content", "multiline": True,
                        "info": "The script or text to be written."}
        }

    def build(self, file_path: str, content: str) -> str:
        try:
            os.makedirs(os.path.dirname(file_path), exist_ok=True)
            with open(file_path, "w", encoding="utf-8") as f:
                f.write(content)
            return f"SUCCESS: File written to {file_path}"
        except Exception as e:
            return f"FAILURE: Could not write file. Error: {str(e)}"

How it works: build_config creates the two fields the agent fills; build creates the folder, writes the file, and returns SUCCESS/FAILURE — the return string lets the agent self‑verify the action and report honestly. This is the bridge between requirement analysis and your IDE: runnable Playwright scripts or BDD feature files land directly in your project folder.

Tool 2 — HTTP Request: point only at test/staging environments so the agent can probe endpoints from the canvas. 🔒 never production.

Backup: after every change, Menu → Export flow as .JSON; keep the JSON and the system prompt under Git.

8. Step 6 — Configure the Guardrails

System Message — paste verbatim into the Agent:

You are 'QA-Agent', a Senior QA Engineer with 10+ years of SDLC expertise (web, API, mobile).
You operate 100% locally and privately.
CAPABILITIES: Test Case Generation, Requirements Gap Analysis, User Story Elaboration,
Bug Triage, Automation Strategy, Security Testing, API Testing.
RULES: (1) base answers ONLY on provided context; (2) state assumptions explicitly;
(3) never fabricate requirements; (4) be deterministic and concise;
(5) output test cases in table format: ID | Precondition | Steps | Expected | Priority;
(6) flag ambiguities as 'GAP-n' with severity;
(7) end every answer with 'Suggested next QA step:'.

Why each rule exists:

RulePurpose
1 — Only provided contextMakes your documents the single source of truth; blocks hallucination.
2 — State assumptionsHumans see exactly what was invented, for review.
3 — Never fabricateProtects traceability and compliance.
4 — Deterministic & conciseStable, documentation‑grade artifacts.
5 — Table formatPaste‑ready for the tracker workbook / TestRail / Excel.
6 — GAP‑n with severityFeeds the GAP Tracker sheet with structured findings.
7 — Next QA stepKeeps the testing workflow moving forward.

Deterministic calibration: set Temperature = 0.1–0.3. Temperature controls sampling randomness; high values make prose creative but test steps flaky. Low values give stable, repeatable results — the same discipline you apply to flaky automated tests, applied to the model.

10. Step 8 — Connect the Tracker Workbook

The companion workbook (qa-findings-tracker.xlsx) turns chat output into auditable QA records across three sheets:

  • GAP Tracker: log of requirement ambiguities with severity, impact, resolution, status.
  • Test Cases: actionable suite linked back to GAPs (traceability).
  • Summary Dashboard: formula‑driven metrics — GAP status/severity counts, TC status counts, Gap‑Linked Test Cases, Active Gap Coverage %.

Paste agent output using identical column headers:

GAP rows → Gap ID | Requirement Section/PRD | Gap Description | Severity | Testing Impact | Suggested Resolution | Status(=Open) | Associated TC ID

TC rows → TC ID | Linked GAP | Test Case Title | Precondition | Test Steps & Input Data | Expected Result | Priority | Status(=Draft)

Workflow rule: every GAP must gain ≥ 1 linked TC (see workbook exemplars: GAP‑1→TC‑3/TC‑4, GAP‑2→TC‑5, GAP‑3→TC‑6, GAP‑4→TC‑7). Color key: edit only white input cells; never overwrite formula‑driven cells.
